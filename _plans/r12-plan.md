# r12 plan: chapters 32 to 35, operating Strimzi on minikube (Opus planner, 2026-11-15)

Status: **draft for owner review.** Branch `release/r12`, cut from main at 2fa9cf3 after r11.0. Existing pins stay frozen: Strimzi 1.3.1, Kafka 4.3.2 (HOLD), CloudNativePG 1.30.1 with operand `18.6-202611090812-standard-trixie`, Kubernetes v1.37.2, minikube v1.39.0, kubectl v1.37.2, otel-lgtm 0.41.0, Debezium 3.7.1.Final, UBI 1.24-20. New components are pinned once, in step 1A, to their latest stable release: kube-state-metrics, the in-cluster registry image, the Debezium PostgreSQL connector plugin archive (3.7.1.Final, the existing Debezium pin, with its sha512), and the digests of the Buildah image that Strimzi 1.3.1 uses for Connect builds. No Helm. kubectl's built-in kustomize. Every apply is `--server-side`.

## Findings that bind the design

These come from reading the r11 artifacts and from the Strimzi 1.3.1 CHANGELOG and `packaging/examples` at tag 1.3.1, fetched while planning. Step 1A records each one as a sources row.

- **Connect build uses Buildah, not Kaniko.** `UseConnectBuildWithBuildah` went GA in 1.3.0 and cannot be disabled. `additionalKanikoOptions` is deprecated. Buildah options and the privileges the build pod needs are G0 Q5. Strimzi's own `kafka-connect-build.yaml` pushes to `ttl.sh`, which this book does not allow. The build output has to go to a registry inside the profile, or there is no build.
- **Resource-state metrics were removed from the operator in 1.2.0.** CHANGELOG: "Removed deprecated resource state metrics - the KSM (kube-state-metrics) should be used instead." Proposal 087 and the blog post "Monitoring of custom resources" (2025-10-01) describe kube-state-metrics with a `CustomResourceStateMetrics` config. Strimzi's example pins `registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.16.0`. So "Monitoring of custom resources" needs a new component (kube-state-metrics).
- **Strimzi Metrics Reporter** works on brokers and controllers (0.48.0) and on Connect, MirrorMaker 2 and the Bridge (0.49.0). It is turned on with `metricsConfig: {type: strimziMetricsReporter}`, and since 1.1.0 its `allowList` can be changed dynamically. Reporter 0.4.0 shipped in 1.2.0. Strimzi ships separate reporter dashboards under `examples/metrics/strimzi-metrics-reporter/grafana-dashboards`.
- **KafkaMirrorMaker2 `v1` shape** is `spec.target` (alias, bootstrapServers, groupId, storage topics) plus `spec.mirrors[].source`. `connectCluster`, `clusters`, `sourceCluster`, `targetCluster` and `heartbeatConnector` are gone. `spec.replicas` is required. The connector `version` fields replace `connector.plugin.version`.
- **Cruise Control auto-rebalance** (0.44.0): `spec.cruiseControl.autoRebalance` with `add-brokers` and `remove-brokers` modes, each naming a `KafkaRebalance` template annotated `strimzi.io/rebalance-template: "true"`. 1.2.0 adds broker cordoning (KIP-1066) during scale-down auto-rebalance on Kafka 4.3 or newer, which applies to 4.3.2. 0.50.1 fixed auto-rebalance on scale up when Cruise Control is not yet ready.
- **Connector offsets through the CR** (0.44.0): `KafkaConnector` and `KafkaMirrorMaker2` manage offsets (list, alter, reset). Since 1.2.0 a connector that asks for `spec.state: stopped` is created stopped. The r04 sources row on the Strimzi blog (Kate Stanley, 2024-11-04) already names the annotation `strimzi.io/connector-offsets` and the ConfigMap holding `offsets.json`. That row says "the Kubernetes mechanics belong to r12".
- **Substrate facts (r11):** the operator watches only `edp-kafka`, so every new CR lives there. `kafka_exec` hard-codes `edp-broker-0`. `_kafka_ready` checks only Kafka `edp`. `load_image` expects `examples/<slug>/<service>/Containerfile`, but example 09 has a root `Containerfile`. `_delete_all_state` deletes Kafka CRs, then apps, then CNPG, then the namespaces. The r11 teardown hang came from a CNPG instance pod with `stopDelay` 1800 s that was still terminating. A Connect worker holding a replication connection to PostgreSQL would bring that hang back, so Connect and MirrorMaker 2 pods have to be gone before the CNPG `Cluster` is deleted.
- **CNPG differs from compose for Debezium.** On compose, `edp` is the initdb superuser and `wal_level=logical` is set by `start.sh`. On CNPG, `edp` is the application owner with no REPLICATION attribute. `wal_level` and the pg_hba rules for logical replication are G0 Q6. Logical replication connections match a pg_hba database entry, not the `replication` keyword (PostgreSQL docs; 1A row).
- **Image rule conflict.** Any Connect image, built by Strimzi or by us, starts from `quay.io/strimzi/kafka:1.3.1-kafka-4.3.2` (UBI-based, published by Strimzi), not from UBI 10. The published `quay.io/debezium/connect` image cannot be used as `KafkaConnect.spec.image`, because Strimzi needs its own image layout. Owner decision 3.
- `validate.py` bans the capitalised word `Manifest` (freight-domain list). Executors write "manifest" in lower case or "release YAML".
- r11 lessons kept: NodePorts answer after rollout (`_wait_apps` polls 30080 and 30082), the field manager names come from `managedFields`, and the CNPG manifest is the "Too long" object. Teardown order is apps, Databases, Cluster, instance pod gone, namespaces.

## Approach

r12 reuses the r11 substrate and extends it. No chapter forks it. The four examples are manifest overlays with a `verify.sh`, a README and an example page, and they contain no Java. Apps are earlier chapters' Quarkus projects deployed unchanged: 02 pair in 32 and 34; 08 order-service and 09 inventory-service in 35; none in 33.

1. **Step 1, in parallel:** survey and sources (1A); G0 spike on one profile (1B); substrate extension built during G0 (1C, orchestrator).
2. **Step 2:** four authoring executors on disjoint files, with no cluster.
3. **Step 3:** one live window on one profile. Chapters 32, 33, 34 and 35 run serially, with fresh namespaces for each `verify.sh` run. Each chapter gets **one** clean run plus each demo switch once (decision 10). Target **at most 2 h**.
4. **Step 5:** a final run on a recreated profile, each chapter once. This is the second clean run.
5. **Step 6:** Opus validation (at most 2 repair rounds), then ship.

Chapter shapes:

- **32 Monitoring Strimzi:** Kafka with `metricsConfig: strimziMetricsReporter` on both pools. The otel-lgtm collector scrapes `/metrics` with a `prometheus` receiver (Kubernetes pod discovery in `edp-kafka`), merged in through `OTELCOL_EXTRA_ARGS` as chapter 26 did. That second pipeline also carries chapter 26's `kafka_metrics` lag receiver. kube-state-metrics adds custom-resource state for Kafka, KafkaNodePool and KafkaTopic, plus the operator's own metrics. One provisioned dashboard `edp-strimzi` sits next to the app telemetry. Apps: the 02 pair.
- **33 Cruise Control:** Kafka with `cruiseControl` and 2 brokers. Catalog topics are KafkaTopics with RF 2, so all replicas sit on brokers 0 and 1. Scaling the pool to 3 leaves broker 2 empty. A `KafkaRebalance` (`add-brokers`, brokers [2]) reaches `ProposalReady` and moves nothing until `strimzi.io/rebalance=approve`; then broker 2 holds replicas. `autoRebalance` with templates is turned on and the pool goes to 4: replicas move with no KafkaRebalance written by hand. If G0 time allows, the pool scales back to 3 and Strimzi empties broker 3 first. Without `autoRebalance` that scale-down is refused (witness). Load comes from `kafka-producer-perf-test.sh` in a broker pod. No apps, no CNPG.
- **34 MirrorMaker 2:** a second Kafka `edp-dr` (one dual-role node) in `edp-kafka` of the same profile, and a `KafkaMirrorMaker2` with target `edp-dr` and source `edp`. It uses `IdentityReplicationPolicy` (decision 8) and short `emit.checkpoints` and `sync.group.offsets` intervals. The 02 pair runs on `edp`, orders O-34xx are processed, then notification-service scales to 0. More orders follow, replication and group offset sync are observed, and notification-service comes back with only `CAMEL_COMPONENT_KAFKA_BROKERS` pointing at `edp-dr`. It resumes from the translated offset, so pre-failover orders are not re-read and post-failover orders are notified. MirrorMaker 2 metrics (replication latency, record count) come through the 32 monitoring base.
- **35 Debezium and Connect on Strimzi:** `KafkaConnect edp-connect` with `use-connector-resources`. `spec.build` declares the `debezium-connector-postgres` 3.7.1.Final plugin with sha512 and outputs to the in-cluster registry (decision 2). Credentials come through `KubernetesSecretConfigProvider` reading `edp-pg-app`. Two `KafkaConnector`s: `order-outbox` (chapter 08's config, host and credentials changed) and `inventory-cdc` (chapter 10's config, the one chapter 10 manages offsets on). The CNPG `Cluster` adds what logical replication needs (G0 Q6). The 08 order-service and 09 inventory-service run unchanged. The section `## Connector offsets in the resource` covers stop through `spec.state`, list to a ConfigMap, alter from a ConfigMap (forward, so a change is skipped, as chapter 10 measured on compose), resume, and the refusal while running. Connect metrics come through the 32 base.

Rejected: Helm for any component; a second minikube profile for 34 (one profile holds both clusters; the PRD allows two profiles only if one cluster cannot show it); external or public registries (`ttl.sh`, Quay or Docker Hub pushes); `minikube docker-env`; Prometheus Operator, PodMonitors and the Helm LGTM charts; Strimzi's example Grafana dashboards copied into the repo (originality rule; our own small dashboard instead); Kafka Exporter (chapter 26's `kafka_metrics` receiver already gives lag); the default MirrorMaker 2 replication policy as the main path (renamed `edp.edp.*` topics are outside the catalog; see Try); Connect metrics in 32 (would name KafkaConnect before 35 introduces it); revising chapter 10 (decision 1).

## Owner decisions (approved 2026-11-15: all recommended defaults)

1. **Chapter 10's Strimzi half lives in chapter 35** as `## Connector offsets in the resource`, running chapter 10's own `inventory-cdc` connector. Chapter 10 stays frozen: no edit, no live run, no forward reference. PRD Q10 is amended to "ch 10 shows the REST form on compose; ch 35 shows the KafkaConnector form on Strimzi", and the CLAUDE.md decisions block records it. *Alternative:* a Strimzi section in chapter 10 with a k8s overlay under `examples/10-*/k8s/`. That puts Part 6 material in Part 2, needs a cluster for a Part 2 chapter, and adds a live run of an old chapter. Not recommended.
2. **Connect build output:** a `KafkaConnect.spec.build` with `output.type: docker` pushing to an **in-cluster registry**. This is a Deployment of the CNCF Distribution image (`docker.io/library/registry:3.x`, Apache-2.0, pinned in 1A) in `edp-kafka`, on emptyDir storage, behind a Service with a **fixed ClusterIP** inside the service CIDR (G0 picks the address), reached over HTTP. The node's containerd pulls the same reference because minikube treats the service CIDR as an insecure registry. If G0 finds it does not, `cluster.sh` adds `--insecure-registry=<service CIDR>`, which is a profile flag and not a host change. The registry is deleted with the namespace on every run, so the image is rebuilt each run and the fresh-state rule holds. *Fallback, decided in G0 only if the build path fails:* a Containerfile `FROM quay.io/strimzi/kafka:1.3.1-kafka-4.3.2` that adds the plugin archive (sha512 checked), built with `docker build`, loaded with `minikube image load`, and referenced by `spec.image` with `imagePullPolicy` handled by Strimzi's `template`. The chapter then teaches Strimzi's documented "your own image" route and states no build-pod claim.
3. **Image-base exception:** the Connect image starts from Strimzi's published Kafka image, not UBI 10. It is recorded next to the pin in `versions.md` and in the CLAUDE.md decisions. Reasons: Strimzi needs its own image layout, and `quay.io/debezium/connect` is not a valid `KafkaConnect` image.
4. **New pins (step 1A, latest stable, open source):** kube-state-metrics v2.x (`registry.k8s.io/kube-state-metrics/kube-state-metrics`, Apache-2.0); the registry image; the Debezium PostgreSQL plugin `debezium-connector-postgres-3.7.1.Final-plugin.tar.gz` from Maven Central with sha512; the digest of the Buildah image the 1.3.1 operator uses (from its Deployment env), recorded rather than chosen. No Kafka, Strimzi or Debezium bump.
5. **Custom-resource monitoring through kube-state-metrics**, with **our own** `CustomResourceStateMetrics` config covering only Ready conditions and a few status fields: `Kafka`, `KafkaNodePool` replicas and nodeIds, `KafkaTopic`, `KafkaRebalance` state, `KafkaConnector`, `KafkaMirrorMaker2`. It lives in `_k8s/monitoring`. Strimzi's example config is cited, not copied. *Alternative:* skip CR monitoring and state that resource-state metrics were removed in 1.2.0. That drops a PRD item.
6. **Dashboards:** one small dashboard of our own per need: `edp-strimzi` (brokers, controllers, operator, CR state, lag) in 32; MirrorMaker 2 and Connect panels added in 34 and 35 as separate provisioned files. Each dashboard is provisioned from a file, as in chapter 26. No Strimzi dashboard JSON enters the repo.
7. **Where the Connect and MirrorMaker 2 metrics appear:** in 35 and 34, through the 32 monitoring base, each with a back link to 32. Chapter 32 covers brokers, controllers, the operator and custom resources, so it has no forward reference.
8. **MirrorMaker 2:** one profile, one namespace, two Kafka clusters: `edp` (the substrate's 1 controller + 1 broker) and `edp-dr` (one dual-role pool `dual`, 1 GiB). Aliases `edp` and `edp-dr`. `IdentityReplicationPolicy`, so mirrored topics keep catalog names and the failed-over app needs only a new bootstrap address. A Try bullet covers the default policy's `edp.` prefix, stated only as measured.
9. **Profile sizing:** keep `--cpus=6 --memory=10g --disk-size=30g`. G0 Q1 measures `docker stats edp` peak for the three heaviest shapes: 33 at four brokers with Cruise Control, 34 with two clusters and MirrorMaker 2, and 35 during the build plus Connect. Move to **12g** if any peak exceeds 8 GiB (80 %), and to **8 CPUs** only if the 33 proposal or the 35 build exceeds its G0 time bound. Host headroom measured at r11 is about 41 GiB available and 16 threads.
10. **Run count, for speed:** in the window, one clean N/N run per chapter, each demo switch once with its failing set frozen, and one bite proof. The second clean run is the final fresh-profile run. r11 did two clean window runs plus the final run. This saves about 30 minutes.
11. **Chapter 33 scale path:** 2 → 3 (manual proposal and approval) → 4 (auto-rebalance on add). The 4 → 3 auto scale-down with cordoning is a check only if G0 measures it at 5 minutes or less; otherwise it is a Try bullet. Brokers in 33 run at 768Mi with a 384m heap (overlay).
12. **Debezium on CNPG:** `Cluster.spec.managed.roles` gives `edp` `replication: true` (declarative, idiomatic CNPG). `publication.autocreate.mode: filtered` stays as in chapters 08 and 10, since Flyway (08) and `psql_exec` (the 10 table) create the tables as `edp`. *Alternative:* a CNPG `Publication` resource with `autocreate.mode: disabled`. Recommended only if G0 Q6 shows `filtered` fails.
13. **Slugs and ids:** `32-monitoring-strimzi`, `33-cruise-control`, `34-mirrormaker-2`, `35-debezium-and-connect-on-strimzi`; order ids `O-32xx` to `O-35xx`; `part: running-on-kubernetes-with-strimzi`. No domain-model change: topics come only from `Topics` 2.4.0, plus Connect, MirrorMaker 2 and Cruise Control internal topics, which are named in prose as infrastructure.

## Per-chapter design

Shared rules: no Java, pom or properties change under `examples/02-*`, `08-*`, `09-*` or `10-*`. Each example holds `kustomization.yaml`, `verify.sh`, `README.md` and an example page. At least two figures per chapter from `diagrams/specs/<NN>-*.py`. Spine per CLAUDE.md, short Build, run, observe, one callout, about 2,000 words (2,500 max). No forward references. Metric names and durations come from G0 only. Demo switches are env vars labelled demo code. Every check number in this plan is indicative; READMEs carry the real list.

### 32 Monitoring Strimzi

Headings: `## Pattern: Metrics from the operator's resources` (problem, solution, how Strimzi models it), `## Brokers and controllers`, `## The operator and its resources`, `## One dashboard beside the flows`, Build, run, observe, When not to use it, References.

Problem: an operator-managed Kafka hides its JVMs behind CRs. Flow dashboards (chapter 26) show lag but not why: a broker under pressure, a controller without a leader, a resource the operator cannot reconcile. JMX scraping per pod with a sidecar config is the old answer.
